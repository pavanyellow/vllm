## Model / serving facts
- **Arch:** ~1T-param MoE. 66 layers, hidden 6144, **256 routed experts, top-6 +
  2 shared (8 active/layer)**, expert intermediate 3072, GQA 64 q / 8 kv heads,
  head_dim 128, vocab 201024. **~37B active params/token.**
- **Quant:** NVFP4 (weights). KV cache **not** quantized (`kv_cache_quant_algo: none`).
- **MoE backend (the thing that mattered on qwen-NVFP4):** auto-selected
  **`FLASHINFER_TRTLLM`** — the native Blackwell FP4 tensor-core path — with
  `FlashInferExperts` + FlashInfer CUTLASS for the unquantized shared/gate path.
  No Marlin/W4A16 fallback; nothing to fix here.
- **Attention:** FlashInfer (sm100). **TP=4** + expert-parallel (`ep:0`, PYNCCL).
  Custom all-reduce enabled (CUSTOM/SYMM_MEM/PYNCCL).
- **Weights:** 137.46 GiB/GPU. **KV cache: 147,229 tokens → 2.25× max concurrency
  @ 65,536 ctx.** (KV is the scarce resource here — the model is ~10× qwen35B, so
  the qwen "KV is unconstrained" story does *not* carry over.)
- **Chunked prefill** on, `max_num_batched_tokens=8192`. CUDA graphs
  **FULL_AND_PIECEWISE**, capture sizes **≤512**. `max_model_len=65536`.
- Startup: weights 39 s, CuTeDSL warmup 130 units/177 s, full engine init 255.7 s.

## T1 — TTFT sweep (C=1, n=8, warm=3, max_tokens=1)
Random ids per iter (no cache). Raw p50/p90/min (ms):

```
 in_len      p50      p90      min
    512     47.1     47.5     46.8
   1024    161.9    162.2    158.3
   2048    163.0    164.9    161.1
   4096    161.8    165.2    159.8
   6144    166.3    168.0    163.4
   8192    200.1    203.6    198.8   <- 1 chunk, full
   8704    243.6    244.0    243.2   <- 2 chunks (8192 + 512)
  12288    319.3    321.3    317.1   <- 2 chunks (8192 + 4096)
  16384    392.7    393.6    390.3   <- 2 chunks (8192 + 8192)
```

Three structural features, all explained:

1. **512→1024 cliff (47 → 162 ms).** The FULL CUDA-graph capture cap is **512
   tokens**. A ≤512-token prefill runs inside a captured graph (no per-kernel
   dispatch) → 47 ms. Above 512 the prefill runs the un-graphed path and pays full
   launch overhead across 66 deep layers → jumps to ~162 ms. This is a *dispatch*
   cliff, not a compute cliff.

2. **Flat ~162–166 ms band, 1024→6144.** TTFT barely moves across a 6× token range.
   Prefill here is **overhead/launch-bound**, not compute-bound: the fixed
   per-forward-pass cost (66-layer launch + ~132 TP all-reduces + weight read)
   dominates; the extra compute for 1k vs 6k tokens is small beside it. Matches the
   qwen daylog's "GPU busy ≪ forward span, big inter-kernel idle" finding.

3. **8192 chunked-prefill sawtooth.** One 8192-chunk = ~200 ms; each additional
   8192-chunk is a *second full pass* (second 37B-active read + all-reduces), so
   8704/12288/16384 climb ~+44 / +119 / +193 ms as the second chunk fills. Per full
   8192-chunk ≈ ~190–200 ms (≈41k prefill tok/s single-stream).

## T3 — Concurrency / aggregate throughput (ctx=1024, gen=128, ignore_eos)
```
   C  agg_tok/s  req_lat_s  ttft_ms_p50
   1      119.2       1.05        161.5
   4      327.6       1.34        237.4
  16      853.4       2.03        464.5
  32     1302.5       2.69        682.1
  64     1883.4       3.72        901.2
```
Aggregate throughput scales **119 → 1883 tok/s (15.8×) from C=1 → 64** and is **not
saturated** at 64. TTFT under load grows 161 → 901 ms (queuing + shared prefill
slots). This is the regime NVFP4's FP4 tensor cores are built for (compute-bound,
batched) — it behaves as expected. Headroom remains: KV supports ~127 concurrent at
this ~1.15k context; the decode graph batch cap is 512.

## Is this "what's expected"? (NVFP4 / 4× B200, prefill)
- **Backend: yes, optimal.** FP4 experts landed on `FLASHINFER_TRTLLM` (native
  tensor-core), attention on FlashInfer sm100. No W4A16/Marlin trap.
- **TTFT ~162 ms @ 1–6k: expected & healthy** for a ~1T-param / 37B-active, 66-layer
  MoE sharded TP=4. (qwen-NVFP4, a ~10× smaller model on a *single* B200, was
  ~182–216 ms at 3–5k; here a far larger model on 4 GPUs is *faster* because TP
  shards the prefill.)
- **512 cliff & 8192 sawtooth: expected structural artifacts**, not regressions —
  they come directly from the graph cap (512) and chunk size (8192), both config
  knobs, not from the FP4 path.
- **KV headroom is the real constraint** (2.25× @ 65k), a direct consequence of
  model size; the qwen "NVFP4 frees KV" result does not transfer.

## T4 — extend FULL CUDA-graph capture to 7168 (the flat-band fix)
Relaunched with `--compilation-config` capture ladder up to **7168**
(`max_cudagraph_capture_size=7168`), `--kv-cache-memory=17179869184` (16 GiB,
manual cap — a C=1 sweep needs almost no KV), `--max-model-len 16384`. Capture cost
was **+0.87 GiB persistent (2.99 vs 2.12 GiB), 16 s** — CuTeDSL kernels were cached,
FP4 path untouched. FULL captured 13 sizes, PIECEWISE 20.

C=1 TTFT p50 (ms), old ≤512 cap vs new ≤7168 cap:

```
 in_len   cap512   cap7168     Δ
    512     47.1     47.0    —     (both graphed)
   1024    161.9     71.6  -56%
   2048    163.0     90.4  -45%
   3072       —     107.0
   4096    161.8    130.0  -20%
   5120       —     152.4
   6144    166.3    168.9   ~0     (crossover)
   7168       —     191.6
   8192    200.1    199.8    —     (above cap, un-graphed control)
```

**The flat ~162 ms band was pure launch/dispatch overhead.** With graphs it becomes a
clean linear ramp: **~52 ms fixed floor + ~19.5 µs/token** (72 ms @1k → 192 ms @7k).
That slope is the real FP4 prefill compute the plateau was hiding behind kernel-launch
idle. Wins are largest at short prompts (−90 ms @1k) and **shrink to zero at ~6144
tokens**, where prefill turns genuinely compute-bound (expert GEMMs) and there's no
launch idle left to remove — so capturing past ~6–7k buys nothing. The 8192 control
(above the 7168 cap) is unchanged, confirming the effect is the graphs, not noise.
This matches the qwen daylog's rule: **graphs help only while launch-bound.**

Takeaway: for the low-concurrency TTFT path, set the FULL-graph ladder to cover your
actual prompt-length distribution up to ~6k; it's nearly free and cuts short-prompt
TTFT ~2×. (Config cost is KV headroom, not GPU memory — size KV for your real
concurrency, not the 16 GiB test cap used here.)

### T4 caveat — that first ladder was NOT Inkling-tuned
The `[1,2,4,8,…512, 768,1024,1536,2048,3072,4096,5120,6144,7168]` ladder was ad-hoc:
the ≤512 part is vLLM's *own auto-default* for Inkling (not copied from qwen — the qwen
`1056` is that model's hybrid-attention block size and is irrelevant here; Inkling's only
prefill boundary is the 8192 chunk), and the >512 rungs I picked by hand just to sample
the curve. Two problems: coarse top-end → pad-up waste (a 6200-tok prompt pads to the
7168 graph), and it *thinned* the fine decode rungs (a batch of 48 pads to 64).

## EC — prefix caching (`enable_prefix_caching` on, 7168-graph server)
Shared fixed prefix (cached after warm) + fresh random suffix each iter. Server-side
`vllm:prefix_cache_hits_total / queries_total` = 301,216 / 974,336 (30.9% blended,
incl. the cold f=0 rows) — confirms real block reuse, not noise.

**EC1 — TTFT vs cache_frac (L=4096, C=1, n=8, warm=3):**
```
  frac cached_tok  TTFT_p50   vs cold
  0.00          0     131.0    1.0x
  0.50       2048      94.3    1.4x
  0.75       3072      76.4    1.7x
  0.90       3686      53.5    2.4x
  0.95       3891      38.9    3.4x
  1.00       4096      23.4    5.6x   (identical prompt / warm re-serve floor)
```
Clean linear law: **TTFT ≈ 23 ms + ~26 µs × *uncached* tokens.** Prefix caching turns
prefill cost from O(full length) into O(suffix); full-hit re-serve bottoms at 23.4 ms.

**EC2 — cold vs 90%-cached across lengths (C=1):**
```
 in_len  cold_p50  cached_p50  speedup
   2048      90.7        35.7    2.54x
   4096     130.3        53.3    2.44x
   7168     192.1        66.0    2.91x
```
Speedup grows with length (more prefix reused). **The two levers stack**: stock-config
cold 4096 (~162 ms) → +graphs 130 ms → +graphs +90% cache **53 ms (~3x)** — the short
suffix prefill is itself graphed. For a repeated-system-prompt workload this is the
single biggest TTFT win available, and it's already on by default.

## EC3 — shared prefix under concurrency (tuned-ladder server, KV 20 GiB/32.3k tok)
Realistic "many users, one long system prompt": fixed 4096-tok prefix + fresh 256-tok
suffix, gen=128, `ignore_eos`. Cold = each request fully random 4352 tok (no sharing).
32 requests per level for a stable estimate.
```
   mode    C  agg_tok/s  ttft_p50  ttft_p90
   cold    1      105.6     144.2     147.5
   cold    4      278.3     269.5     446.6
   cold    8      413.1     467.6     651.9
   cold   16      567.2     714.4    1257.1
 cached    1      117.0      38.1      38.4
 cached    4      370.3     105.7     111.6
 cached    8      626.7     144.5     151.3
 cached   16     1122.6     215.8     237.7
```
At C=16, shared-prefix caching = **2.0× throughput (1123 vs 567 tok/s) and 3.3× lower
TTFT (216 vs 714 ms)**. Two compounding effects: (1) the 4096-tok prompt is stored
**once** — cold packs 16×4352 ≈ 70k tokens > the 32.3k-token KV → queuing (throughput
tail flattens 413→567), while cached ≈ 4096 + 16×384 ≈ 10k fits, so all 16 run; (2)
only the 256-tok suffix is prefilled per request, and it's graphed. Cold scales 5.4×
(C1→16), cached 9.6×. **On a small-KV / big-model box like this, prefix sharing is a
throughput lever, not just a TTFT one** — it multiplies effective KV.

## Levers (prefill / throughput only)
- ✅ **Raise the FULL CUDA-graph capture cap above 512** → **DONE (T4)**: ladder to
  7168 cut TTFT ~2× for ≤2k prompts, ~0 cost. Effective up to the ~6k compute-bound
  crossover; no point past that.
- **Raise `max_num_batched_tokens` past 8192** → push the sawtooth boundary out so
  long prompts prefill in one pass (costs transient activation memory; watch the
  147k-token KV budget).
- ✅ **Prefix caching** → **DONE (EC1/EC2)**: 90% cached prefix = 2.4–2.9× TTFT,
  full re-serve = 5.6× (23 ms floor). Stacks with graphs. On by default.
- ✅ **Shared-prefix under load** → **DONE (EC3)**: one cached system prompt = 2.0×
  throughput + 3.3× lower TTFT at C=16; multiplies effective KV on this small-KV box.

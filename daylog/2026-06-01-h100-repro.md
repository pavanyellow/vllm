with the sawtooth gone: every E8 slow-band length (3000/4000/4096/4752/5000, all

box/driver delta (driver 580.126.09, CUDA 13.0 here) — the shape of the result
(flat band, no sawtooth, monotonic prefill-compute rise) is identical. Headline
E9 conclusion holds: **block=8192 removes the chunked-prefill sawtooth, up to ~2×

## E9-repro-3 — short-prompt floor 10→800
`python ttft_sweep.py --lengths 10,32,64,128,256,384,512,640,768,800 --concurrency 1 --n 12 --warm 4`
(same server/method). Probes the memory-bound floor below the compute-bound rise.

| in | p50 | p90 | min |
|---:|---:|---:|---:|
| 10 | 21.9 | 22.5 | 21.5 |
| 32 | 75.5 | 76.2 | 75.0 |
| 64 | 77.8 | 79.9 | 74.8 |
| 128 | 79.1 | 79.4 | 76.6 |
| 256 | 78.9 | 83.3 | 75.2 |
| 384 | 73.9 | 75.4 | 71.5 |
| 512 | 75.2 | 76.5 | 73.4 |
| 640 | 75.6 | 79.2 | 71.5 |
| 768 | 76.1 | 77.0 | 74.7 |
| 800 | 75.6 | 76.3 | 74.7 |

Two regimes:
- **L=32→800: flat ~74–79 ms plateau, L-independent.** This is the memory-bound
  prefill floor — TTFT here is the one-time ~32 GB FP8 MoE weight read + fixed
  overhead, not token compute (adding 768 tokens costs ~0 ms). It joins continuously
  to the compute-bound rise measured above: floor ~75 → 95 ms @4200 (E10 wall) →
  153 ms @8100. The compute term only becomes visible above ~1k tokens.
- **L=10 = 21.9 ms — sub-floor.** Falls ~53 ms *below* the plateau because 10 tokens
  × top-8 ≈ 80 expert activations only touch ~70 of 256 experts (coupon-collector
  on 256), so most expert weights are never read this prefill → the dominant HBM
  cost is skipped. Consistent with E6's "all 256 experts hit at L=4096"; the full
  32 GB read (and thus the full floor) only materializes once L·8 ≳ 256, i.e. by
  L≈32 here. So the floor is set by *expert coverage*, not a fixed launch cost.

Whole-curve picture (block=8192, C=1): 22 ms @L=10 → ~75 ms floor (32–800) →
slow compute-bound rise → 153 ms @8100, one clean monotonic line, no sawtooth.

> **Correction (see E-repro-4):** the "coupon-collector / expert-coverage sets the
> floor" claim above is **wrong** — a finer 1→128 sweep shows a *step function*, not
> a smooth coverage ramp, and the floor turns out to be host-dispatch-bound (E-repro-6),
> not the weight read. Kept here as written for honesty; superseded below.

`ttft_sweep.py --lengths 1,2,4,6,8,10,12,14,16,20,24,28,32,40,48,56,64,96,128 --n 16 --warm 4`

Four flat plateaus with sharp jumps: 14.7 (L=1) → ~22 (L=2–16) → ~71 (L=20–28) → ~75

does **not** explain the step — falsifying E-repro-3's coverage story. Kernel COUNT is
~constant (~1720) across L=15/25/300 too, so the step isn't more kernels either.

## E-repro-6 — clean host/device decomposition, L=15/300/4000
Relaunched profiler with `with_stack=false, record_shapes=false` (the stack-unwind added
~8 ms wall). `execute_context` annotation = the forward window.

| metric | L=15 | L=300 | L=4000 |
|---|--:|--:|--:|
| wall TTFT (clean) | 26.5 ms | 81.7 ms | 89.3 ms |
| GPU busy | 9.65 ms | 15.72 ms | 62.77 ms |
| **GPU utilization** | 34% | **19%** | **70%** |
| device kernels | 1723 | 1719 | 1712 |
| avg kernel exec | 5.6 µs | 9.1 µs | 36.7 µs |
| `cudaLaunchKernel` total | 3.64 ms | 4.23 ms | 3.91 ms |
| sync/event time | ~0 | ~0 | ~0 |
| inter-kernel gap mean | 13.4 µs | **39.5 µs** | 12.1 µs |
| inter-kernel gap **median** | **0.2 µs** | **35.7 µs** | **1.3 µs** |

Empirics: kernel count (~1720), `cudaLaunchKernel` API time (~4 ms), and sync (~0) are
**constant** across all three. What moves: avg kernel exec (5.6→9.1→36.7 µs → GPU busy)
and the median inter-kernel gap. L=300 is uniquely starved — the GPU waits ~36 µs before
*every* kernel (median 35.7 µs vs 0.2 at L=15, 1.3 at L=4000). The launch *syscall* is
only ~4 µs of that gap; the rest is host-side eager traversal between kernels (top CPU
ops: `vllm::moe_forward_shared` ×40, `vllm::qwen_gdn_attention_core` ×30). Prefill is not
graph-captured (CUDA graphs are decode-only here) → eager per-kernel dispatch. So the
~75 ms floor is **host-dispatch / GPU-starvation bound at L=300**, not the weight read.
(Open: why L=15 stays fed at 0.2 µs gaps while L=300 starves at 36 µs — not resolved.)

## E-repro-7 — is the MoE bandwidth-bound? (`fused_moe_kernel` identity + bytes)
The dominant device kernel is the generic **Triton** `fused_moe_kernel` (×80 = 40 layers ×
{gate+up `w13`, down `w2`}); full trace name is literally `fused_moe_kernel` (no mangling).
Server auto-picked the **TRITON** MoE backend (DEEPGEMM/FLASHINFER_* compiled-in but gated
out at `N=512`); dense FP8 linears already use DeepGEMM. Untuned (E11 config still missing).

Config-derived weights (FP8 on disk, `F8_E4M3` — **not** FP16): per routed expert 3.15 MB
(`w13` 2.10 + `w2` 1.05); ×256 = 805 MB/layer; **×40 = 32.2 GB**. Measured achievable HBM
on this card (torch microbench): **2.95 TB/s** read (spec 3.35). One full weight read floor
= 32.2 GB / 2.95 = **10.9 ms**. MoE GEMM compute @FP8 peak: 0.008 ms (L=300), 0.10 ms
(L=4000) → **never compute-bound**.

`ncu` was installed (`nsight-compute-2026.2.0`) to get exact DRAM bytes but is **blocked**
in this container: `ERR_NVGPUCTRPERM` (perf counters admin-gated, no CAP). Fell back to a
standalone single-layer `fused_experts` timing **staircase** (256 experts, top-8, fp8
block `[128,128]`, all 256 active even at L=300):

| L | tok/exp | M-tiles@64 | ms | L | tok/exp | M-tiles | ms |
|--:|--:|--:|--:|--:|--:|--:|--:|
| 512 | 16 | 1 | 0.357 | 2600 | 81 | 2 | 0.592 |
| 2000 | 62.5 | 1 | 0.481 | 4096 | 128 | 2 | 0.758 |
| **2048** | 64 | 1 | 0.485 | **4200** | 131 | 3 | 0.773 |
| **2100** | 65.6 | 2 | 0.501 | 8000 | 250 | 4 | 1.242 |

**No staircase.** Crossing the `BLOCK_M=64` tile boundary (1→2 tiles at L=2048→2100) adds
only **+3%** (0.485→0.501 ms), not the +60–100% a full DRAM weight re-read would cost; the
2nd tile is ~free (consistent with L2 reuse — one expert's 3.1 MB ≤ 50 MB L2 — though
unconfirmed without counters). Time instead rises ~linearly with tokens. So:
- small L (≤2048, 1 tile): ~weight-BW-bound, reads 0.8 GB/layer at ~2.3 TB/s;
- large L: time ∝ tokens → per-token activation + compute, **not** weight re-reads.

> **Correction:** an earlier in-session claim that L=4000 moves "~68 GB (2× weight
> re-read)" is **retracted** — it assumed the kernel saturates 2.95 TB/s, which the
> staircase falsifies. Also nuances E10's "MoE memory-bound, 2.5× over roof": part of
> that 2.5× is per-token activation traffic, not weight-BW inefficiency.

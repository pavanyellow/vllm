## Experiment 1 — TTFT sweep 3500→4500, concurrency 1 (B200)

`ttft_sweep.py --start 3500 --stop 4500 --step 100 --concurrency 1 --n 20 --warm 4`
(unique random token-id prompts, 0% prefix-cache hit **verified** in server logs,
5 output tokens, TTFT = send → first streamed token).

| input tokens | TTFT p50 (ms) | TTFT p90 (ms) | TTFT min (ms) |
|---:|---:|---:|---:|
| 3,500 | 117.3 | 127.0 | 112.6 |
| 3,600 | 117.4 | 123.3 | 112.3 |
| 3,700 | 175.6 | 190.6 | 168.5 |
| 3,800 | 173.4 | 178.3 | 165.0 |
| 3,900 | 194.0 | 200.1 | 168.6 |
| 4,000 | 184.9 | 197.9 | 174.4 |
| 4,100 | 186.8 | 192.7 | 179.0 |
| 4,200 | 182.5 | 191.8 | 172.0 |
| 4,300 | 124.3 | 133.5 | 117.3 |
| 4,400 | 133.3 | 138.2 | 125.1 |
| 4,500 | 136.1 | 140.3 | 128.3 |

**Sawtooth, same shape as H100 (BENCHMARKS.md §C.3).** A high band
(~175–194 ms) sits between two lower plateaus: ~117 ms below 3,700 and
~124–136 ms above 4,200. The step-up is between 3,600→3,700; the step-down
between 4,200→4,300. On H100 those edges were ~3,584→3,712 and
~4,096→4,224 — so the band is shifted slightly and drops a bit later here.

**B200 is NOT faster than H100 in this range.** Peak band ~185–194 ms vs
H100's ~165 ms (§C.3). At ~4k single-stream prefill the path is
latency/overhead-bound, not FLOP-bound, so B200's extra compute doesn't help
(and kernel/scheduling differences can make it marginally slower). Expect the
B200 win to show up only at much longer inputs / higher concurrency, where
prefill is actually compute-bound.

## Experiment 2 — same sweep with HTTP connection pooling

Changed `ttft_sweep.py` to reuse one persistent `requests.Session` (keep-alive,
`HTTPAdapter` pool sized to `--concurrency`) instead of a fresh `requests.post`
per call, to strip per-request TCP connect/handshake out of the client TTFT.

Same command, re-run:

| input tokens | p50 pooled (ms) | p50 prev (ms) |
|---:|---:|---:|
| 3,500 | 131.9 | 117.3 |
| 3,600 | 130.4 | 117.4 |
| 3,700 | 182.8 | 175.6 |
| 3,800 | 178.8 | 173.4 |
| 3,900 | 187.5 | 194.0 |
| 4,000 | 190.6 | 184.9 |
| 4,100 | 191.8 | 186.8 |
| 4,200 | 183.8 | 182.5 |
| 4,300 | 127.0 | 124.3 |
| 4,400 | 122.9 | 133.3 |
| 4,500 | 120.7 | 136.1 |

**Verdict: connection setup was negligible.** Deltas are within run-to-run
noise and bounce both directions (pooled is even a touch *higher* at the low
plateau). On loopback the TCP handshake is sub-ms and is dwarfed by server-side
prefill+decode — so the earlier "HTTP overhead" caveat is real but <~1–2 ms,
below measurement noise. Pooling kept as standard hygiene (and it matters more
at higher concurrency / over a real network).

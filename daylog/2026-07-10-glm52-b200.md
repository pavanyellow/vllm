# 2026-07-10 — GLM-5.2-FP8 on 8×B200: setup + smoke test

Goal: characterize cold TTFT for the voice workload (C=1, 3–5k token prompts) on
`zai-org/GLM-5.2-FP8` (743B MoE / 39B active, MLA + DSA sparse attention, 78 layers,
256 experts top-8, MTP-5). Same method as the Qwen3.6 study (see daylog README).

Theory (done previously, not re-derived here): weight-read floor at 4k ≈ 12 ms
(750 GB FP8 ÷ 64 TB/s), honest floor ≈ **20 ms** (11.3 expert read + ~4.5 attn/dense
compute + 2–3 comms + ~2 dispatch). Expected recipe-verbatim ≈ 100–200 ms (78-layer
eager dispatch); tuned target ~40–60 ms cold / ~25 ms warm.

```bash
vllm serve zai-org/GLM-5.2-FP8 --served-model-name glm-5.2-fp8 \
  --host 0.0.0.0 --port 8080 --tensor-parallel-size 8 --kv-cache-dtype fp8_e4m3 \

  --max-num-batched-tokens 8192 --max-num-seqs 32 \

  --default-chat-template-kwargs '{"enable_thinking":false}' \
  --reasoning-parser glm45 --tool-call-parser glm47 --enable-auto-tool-choice
```

(thinking OFF is mandatory for voice — GLM defaults to Think Max ≈ 10 s to first content)

Deltas vs the official recipe (recipes.vllm.ai/zai-org/GLM-5.2?hardware=b200),
all deliberate: recipe sets `VLLM_DEEP_GEMM_WARMUP=skip` (faster startup, first
requests JIT instead) — we keep warmup ON so measurements never pay compile;
we add `--max-model-len 32768` (voice path; recipe targets 1M ctx),
`--gpu-memory-utilization 0.85`, `--max-num-batched-tokens 8192`, and the
thinking-off template kwargs. Rest is recipe-verbatim (TP8, fp8_e4m3 KV, MTP-5,
max-num-seqs 32, glm45/glm47 parsers).

**Attempt 1 failed at +16 min**: FlashInfer JIT (`trtllm_fused_moe_kernel_launcher.cu`,
compiled during warmup) died with `fatal error: nvrtc.h: No such file or directory` —
the third instance of the same image gap (missing CUDA dev headers). Durable fix
instead of per-process env: symlinked all 50 headers present in the torch nvidia
wheel (`site-packages/nvidia/cu13/include/*.h`) but absent from
`/usr/local/cuda/include`. Attempt 1 timings still valid and recorded below;
attempt 2 relaunched 21:47 PT (torch.compile AOT cache now warm, ~220 s saved).

## E2 — kernel-level profile

Server relaunch (config identical to E3) + `--profiler-config.profiler torch
--profiler-config.torch_profiler_dir /workspace/traces
--profiler-config.torch_profiler_with_stack false`. Note for reproducers: the
`VLLM_TORCH_PROFILER_DIR` env is dead in 0.23 — without profiler-config the
/start_profile route isn't even mounted (two relaunches wasted learning this).
Traces: 3 captures (cold 4k, 16-tok floor, warm 4k @0.95 cache), 8 rank files
each; analysis = rank0, `analyze_trace.py` (bucket Σ of GPU kernel time +
busy/idle from merged stream intervals). Profiler inflates wall (~120 ms span
for the 72 ms floor case); ratios are the signal, not absolute spans.

Bucket caveat kept honest: the `bmm_E4m3*`/`bmm_Bfloat16*` kernels (×76 ≈ one
per MoE layer) are the FLASHINFER_TRTLLM expert GEMMs, not dense GEMMs — the
table below reassigns them.

**cold4k** — span 204.3 ms, GPU busy 196.5 ms (**96% — no dispatch bubble left**):

```
MoE expert GEMMs (bmm fc1 21.9 + fc2 14.0 + finalize/act 17.4)   ~53 ms   ~5x roof
MLA prefill fmha (fmhaSm100 QkvE4m3 HQk576HV512 TokenSparse)     ~46 ms   ~10x theory
all-reduce (multimem_all_reduce x160)                            ~26 ms
quant/cvt (per_token_group_quant x1074 tiny launches)            ~21 ms
copy/misc                                                        ~18 ms
DeepGEMM dense projections                                        ~8 ms
DSA indexer                                                       ~1.6 ms  << negligible
```

- **The 38 ms/1k slope is real compute, split ~half MoE GEMM / ~half MLA fmha**,
  both far off roofline. The "immature DSA indexer" hypothesis is falsified —
  the indexer is 0.8% of GPU time; the sparse-attention cost lives inside the
  fmha prefill kernel instead.
- **floor16** — comms 57% of Σ: `allreduce_fusion_oneshot_lamport` ×158 @ ~350 µs.
  The 72 ms floor is structural TP8: 2 all-reduce latency hops × 78 layers
  (+MTP), plus ~32 ms weight-read-bound small GEMMs. E4 (EP layouts / fewer
  hops) is the attack; kernel tuning won't move it.
- **warm4k** — GPU idle 38% of span: short MTP-verify steps between small graphs
  leave scheduling gaps. Headroom exists below 73 ms warm.
- Curious: tiny batches route all-reduce to flashinfer oneshot-lamport (~350 µs/
  call profiled) while 4k uses multimem (~140 µs/call) — worth an A/B later.

## Load test — TTFT vs concurrency (E3 config, cold, simultaneous arrivals)

`ttft_sweep.py --concurrency C` fires C identical-length requests together and
times each. p50 across all requests, 12 rounds, 4 warmup.

```
 in_len   C=1     C=2     C=4      C=8      (p50 ms)
   3000   158     264     494      643
   4000   198     343     654      974
   5000   239     453     672     1315
```

- Prefill is compute-bound → colliding cold turns queue: C=2 ≈ 1.7×, C=4 ≈ 3.3×,
  C=8 ≈ 5–5.5× solo. C=8 p90 @5k = 1623 ms.
- min stays ~347 ms at 4k for C≥2: max-num-batched-tokens=8192 fits ~two 4k
  prefills per batch; the rest is queue position (p50↔p90 spread).
- Market read: our C=8 numbers land exactly in the 0.8–1.4 s band the
  fleet-loaded providers show — consistent with "their TTFT is queueing
  economics, not kernels". Dedicated C=1 (and 73 ms warm turns) is the edge.
- Product guidance: cap concurrent *cold prefills* per replica at ~2 to hold
  <350 ms; warm turns are cheap and barely collide.

Warm-path variant (cache-frac 0.95, same ladder):

```
 in_len   C=1     C=2     C=4     C=8      (p50 ms)
   3000   71.5    78.1    99.9   152.2
   4000   71.9    84.3   116.1   158.9
   5000   72.2    86.6   122.4   185.5
```

- **8 colliding warm turns stay under 190 ms p50 (p90 ≤ 189)** — ~2.5× the solo
  floor vs ~5× for cold. Each warm turn adds only ~10 ms compute on the shared
  72 ms comms floor, so warm collisions are nearly free.
- Product: replica sizing is set by cold-start collision probability, not by
  steady-state warm traffic.

## E2b — roofline: bound-type per component (session cut short here; box killed)

Method: profiler traces at L=1000/2000/4000/8000 cold (unprofiled TTFT refs
86/122/198/357 ms; profiled spans 133/135/207/400). Rank0 bucket Σ vs an
analytic per-GPU roofline (`roofline.py`, peaks 4.5 PF FP8 + 8 TB/s HBM/GPU,
NVLink multimem ~675 GB/s eff): at 4k the model forward should cost ~27 ms
(MoE weight-read 11.3 mem-bound + allreduce 11.4 BW-bound + ~4 ms compute);
measured GPU-busy is 199 ms → 7.4× off in aggregate. GPU-busy 96-97% at ≥4k
(dispatch solved); 39% idle at 1k (floor is latency, not kernels).

Measured Σ scaling (rank0, ms at 1k/2k/4k/8k) vs roof:

```
component        1k     2k     4k     8k    roof@4k  gap@4k  bound (verdict)
fmha prefill     5.0   15.9   42.9   97.0     ~0.9     ~48x  compute, kernel immature
allreduce x160   6.9   15.5   24.3   75.4    ~11.4    ~2.1x  BW-bound large / latency small
MoE bmm+aux     18.3   26.4   36.3   55.0    ~11.3    ~3.2x  mem-bound (weight read)
quant_cvt        8.6   12.8   21.0   36.2     ~0       n/a   pure overhead (1074 launches)
copy_misc        8.0   11.0   18.3   33.2     ~0       n/a   pure overhead
DSA indexer      0.7    0.9    1.6    4.1     ~0.1     small negligible at all L
```

Verdicts:

1. **fmha prefill is the #1 lever.** Scales superlinearly *past* the DSA
   index_topk=2048 boundary (2k→4k: 2.7×, 4k→8k: 2.3× — should go linear if
   sparsity applied) and sits ~48× over its compute roof at 8k. The
   FLASHINFER_MLA_SPARSE "TokenSparse" prefill kernel does not appear to
   exploit DSA sparsity. **Next: A/B `--attention-backend FLASHMLA_SPARSE`**
   (also unlocks fp8_ds_mla KV format).
2. **All-reduce #2.** 2.1× off BW roof at 4k, 3.3× at 8k; at the 72 ms floor
   it's 57% of kernel time as ~160 latency hops. Levers: E4 EP (unfinished —
   launch existed, killed for demo), allreduce backend forcing, fusion.
3. **MoE expert GEMMs are the closest to roof** (~1.6× at 1k where purely
   weight-read; 3.2× at 4k). TRTLLM bmm path is decent; DEEPGEMM MoE A/B is
   a moderate lever at best. The 11.3 ms weight-read floor matches theory
   exactly.
4. **Quant + copies = ~18% of GPU time with no roofline term** (per-token-group
   quant ×1074 + scatter/convert launches). Fusion opportunity, matches the
   Qwen study's "fusable overhead" bucket.

Honest gap ledger @4k: measured busy 199 ≈ fmha 43 + allreduce 24 + MoE 36 +
quant 21 + copy 18 + dense/proj ~35 + attn-aux ~3 + misc ~19. Closing fmha to
5 ms, allreduce to 12, quant+copy to 8 → ~120 ms saved → cold 4k TTFT ~80 ms
plausible on this hardware/software once attention is fixed; the 72 ms floor
needs the comms-latency work (EP / fewer hops) to move below ~40 ms.

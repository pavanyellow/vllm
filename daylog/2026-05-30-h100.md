## E9 — block_size=8192 kills the sawtooth (verify)
Knob (`--help`): `--block-size N` (CacheConfig, default None→derived 1056) sets the attention KV block; chunk boundary follows it. `--block-size 8192` → prompts ≤8192 prefill in ONE chunk (one 40-layer pass).

OOM on the way (B200 had room; H100 80GB doesn't). Unified allocator forces mamba_page == attention_page; mamba state is fixed/seq, attention page ∝ block.
- Padding mamba: 1056 → +0.76%; 8192 → +681.68%. (1.068168/1.0076 = 7.758 = 8192/1056 ✓.)
- attn page/token = 10 full-attn × 2(KV) × 2 kv-heads × 256 head_dim × 2B = 40 KiB/tok. → page 1056=41.25 MiB, 8192=320 MiB. So mamba state ≈41 MiB/seq (why 1056 exists); at 8192 each slot bloats to 320 MiB (6.76× waste).
- OOM was the mamba cache (8.00 GiB ≈ 25 slots × 320 MiB), independent of max-model-len (32768 vs 8192 → identical 8 GiB). Fix = bound slots: `--max-num-seqs 8` → 2.5 GiB. Started OK: KV 35.94 GiB → 269,165 tok, 32.9× @8192 (vs 1.39M @1056 — big-block granularity cost; fine for C=1).

Server: `... --max-model-len 8192 --max-num-seqs 8 --block-size 8192` (rest as Setup). Same E8 grid:

## E10 — per-component prefill profile + H100 roofline, L=4200, block=8192, 1 pass
`prof_prefill.py --len 4200` (warm 4; /start_profile → 1 prefill max_tokens=1 → /stop_profile; bucket device-kernel dur from worker trace by name regex — committed tool). Roofline = E6 method on H100 specs (dense FP8 1.979e15 FLOP/s, HBM3 3.35e12 B/s); per-tok FLOP & per-layer wt bytes are arch-derived (reused from E6), re-evaluated max(t_comp,t_mem) at L=4200, regrouped into the measured buckets.

| bucket | meas ms | H100 roof ms | ratio | roofline maps to |
|---|--:|--:|--:|---|
| MoE expert GEMM (fused_moe) | 23.73 | 9.61 | 2.5× | experts, memory-bound (32.2 GB wt read) |
| dense proj (lin+full proj, shared, router) | 11.19 | 4.63 | 2.4× | compute |
| elementwise/norm/copy | 9.73 | ~0 | — | overhead, no roofline term |
| lin_attn scan/conv (gated-deltanet) | 9.61 | 0.07 | ~140× | E6 models scan as O(L) recurrence — wrong |
| FP8 dynamic quant | 5.13 | 0 | — | overhead |
| MoE route/act/finalize | 2.92 | ~0 | — | overhead |
| full attn (fmha) | 2.10 | 0.74 | 2.9× | compute (∝L) |
| OTHER (unnamed triton) | 1.95 | 0 | — | — |
| Σ GPU busy | 66.35 | 15.05 | 4.4× | |
| wall (TTFT) | ~95 | 15.05 | 6.3× | +~29 ms launch bubble |

wall = clean no-profiler value (E9 band); profiler-enabled server reads ~105 ms (instrumentation) — GPU-busy from trace is unaffected. Three gap sources: (1) **gated-deltanet scan ~140×** — E6's O(L) recurrence is wrong; chunked kernel materializes matmuls (DeltaRule 6.1 + causal_conv1d 2.0 + post_conv 1.5). (2) **~20 ms (30%) overhead** with no roofline term: FP8 quant 5.1 + routing 2.9 + elementwise/norm 9.7. (3) real matmuls **2.4–2.9×** over roof. H100 HBM3 (3.35 TB/s) makes the MoE weight-read memory-bound — 9.6 ms, the largest roof term.

## E11 — MoE config tuning (NULL result)
Startup warns `fused_moe.py:1073 Using default MoE config ... file not found: E=256,N=512,...H100_80GB_HBM3,dtype=fp8_w8a8,block_shape=[128,128].json`. No tuned file shipped for this fine-grained-MoE shape on H100 (B200/H200 have it). Fallback `get_default_config`: BLOCK_M=64, N=K=128 (pinned by block_shape), GROUP_M=32, warps=4, stages=3.
Tuned: `benchmarks/kernels/benchmark_moe.py --model …FP8 --dtype fp8_w8a8 --tune --batch-size 4200` (640 cfgs after fp8-block filter; N,K pinned → only BLOCK_M/GROUP_M/warps/stages free). Winner: GROUP_M=16, stages=4 (only diff from default).
MoE bucket @L=4200: default **23.73 → tuned 23.60 ms (0.5%, noise)** (tuned stable 23.59–23.62). **Null** — config can't help: MoE is memory-bound on the 32 GB weight read (per-expert intensity 2M≈256 FLOP/B < H100 ridge 591), so tiling/pipeline tweaks don't move it. The "missing config" warning is a perf red herring here. Tuned JSON committed to repo `configs/` anyway (silences warning, no harm).

## E12 — DeepGEMM MoE backend (forced)
Auto picks TRITON `fused_moe_kernel` for experts; the fp8 oracle filters DEEPGEMM as unavailable for this shape (it's higher priority but gated). `--moe-backend deep_gemm` forces it → log `Using DEEPGEMM Fp8 MoE backend`; runs for real (TritonOrDeepGemmExperts → DeepGEMM grouped GEMM, `fused_moe_kernel` gone from trace).
Profile L=4200, block=8192, 1 pass (total GPU busy, 4 samples each, non-overlapping):
- MoE matmul kernels: Triton `fused_moe` 23.6 → DeepGEMM grouped **21.7 ms (~8% faster kernel)**.
- But DeepGEMM needs contiguous-per-expert layout → adds grouping/`transpose_fp32`/permute (~+3 ms, lands in OTHER) that Triton does inline.
- **Total GPU busy: 66.3 → 65.4 ms** (Triton 66.07–66.64; DeepGEMM 65.24–65.56 → real ~1.4%).
Net: DeepGEMM's expert matmul is genuinely ~8% faster, but grouping overhead claws most back → ~1.4% end-to-end. That's why auto skips it at small N=512. Real but modest (vs E11 null). Lever, not jackpot — the MoE floor is still the 9.6 ms weight read (E10).

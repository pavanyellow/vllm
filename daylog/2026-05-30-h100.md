## E9 — block_size=8192 kills the sawtooth (verify)
Knob (`--help`): `--block-size N` (CacheConfig, default None→derived 1056) sets the attention KV block; chunk boundary follows it. `--block-size 8192` → prompts ≤8192 prefill in ONE chunk (one 40-layer pass).

OOM on the way (B200 had room; H100 80GB doesn't). Unified allocator forces mamba_page == attention_page; mamba state is fixed/seq, attention page ∝ block.
- Padding mamba: 1056 → +0.76%; 8192 → +681.68%. (1.068168/1.0076 = 7.758 = 8192/1056 ✓.)
- attn page/token = 10 full-attn × 2(KV) × 2 kv-heads × 256 head_dim × 2B = 40 KiB/tok. → page 1056=41.25 MiB, 8192=320 MiB. So mamba state ≈41 MiB/seq (why 1056 exists); at 8192 each slot bloats to 320 MiB (6.76× waste).
- OOM was the mamba cache (8.00 GiB ≈ 25 slots × 320 MiB), independent of max-model-len (32768 vs 8192 → identical 8 GiB). Fix = bound slots: `--max-num-seqs 8` → 2.5 GiB. Started OK: KV 35.94 GiB → 269,165 tok, 32.9× @8192 (vs 1.39M @1056 — big-block granularity cost; fine for C=1).

Server: `... --max-model-len 8192 --max-num-seqs 8 --block-size 8192` (rest as Setup). Same E8 grid:

Cost: KV capacity 1.39M→269k tok (mamba 6.76× waste/slot) — acceptable at low concurrency; revisit if serving many concurrent seqs.

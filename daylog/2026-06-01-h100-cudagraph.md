# 2026-06-01 (H100) — CUDA-graph capture is the TTFT dispatch floor

Pursuing the lever the repro log kept pointing at: prefill is **host-dispatch bound**
(`2026-06-01-h100-repro.md` E-repro-6: L=300 = 81 ms wall / 15.7 ms GPU-busy = 19% util,
~60 ms eager-launch idle; the unexplained L=16→20 floor step in E-repro-4). A collaborator's
A100/INT8 report (`serve-qwen36-a100` branch) found vLLM only graph-captures **decode** sizes,
so prefill runs PIECEWISE/eager — and extending captures gave −40–65% TTFT. Checked it against
our FP8/H100 setup; it transfers. Same box/model as the repro log.

## Root cause: the capture cliff = our `--max-num-seqs 8`
The recommended config's `--max-num-seqs 8` caps `max_cudagraph_capture_size` at **16**:
```
cudagraph_capture_sizes: [1, 2, 4, 8, 16]      # mixed prefill-decode, PIECEWISE
```
So prefill ≤16 tokens runs a captured graph; **>16 falls to no-graph (eager)**. Runtime maps a
request of N tokens to the smallest captured rung ≥ N (`cudagraph_dispatcher.py:76-95`, round-up);
N > max → `CUDAGraphMode.NONE`. This is exactly the E-repro-4 floor step at L=16→20.

## How to set it / cost
- CLI: `--compilation-config '{"cudagraph_capture_sizes":[...]}'` (max rung → `max_cudagraph_capture_size`).
- Memory is set by the **largest** rung (one persistent workspace), not the count; rung count only
  costs capture time (~0.13 s/rung small) + padding granularity (round-up to next rung).

## G4 — block=8192 vs CUDA graphs: a hard conflict; default block=1056 fits
Extending the ladder past ~104 **OOMs on `--block-size 8192`**: the 8192-token attention block makes
each graph's attention scratch huge — the 512 rung alone needs an **8 GiB** workspace (104 rung = 0.28 GiB).
At util 0.90/0.80/0.65 it still OOMs (KV granularity at block=8192 is too coarse to free room). Dropping
back to **default block=1056** fixes it: the same ladder→512 captures in **0.38 GiB**. So the E9
sawtooth-killer (block=8192) and the CUDA-graph fix **conflict** — same catch-22 as block=8192-vs-caching.
For L≤500 (< one 1056 block) there's no sawtooth on either block, so block=1056 is strictly better here.

`vllm serve` (default block=1056, ladder→512, util 0.90):
```bash
vllm serve Qwen/Qwen3.6-35B-A3B-FP8 --served-model-name Qwen/Qwen3.6-35B-A3B \
  --max-model-len 8192 --gpu-memory-utilization 0.90 \
  --enable-prefix-caching --enable-chunked-prefill --language-model-only \
  --reasoning-parser qwen3 --default-chat-template-kwargs '{"enable_thinking":false}' \
  --max-num-batched-tokens 8192 --max-num-seqs 8 \
```

## G5 — graphs→1056 shrink the 3k–5k sawtooth ~3× (predicted, then confirmed)
Hypothesis (from the mechanistic model below): the 2-pass for a non-aligned 4k prompt is `[3168 + 832]`;
the **832 remainder chunk is ≤1056 → graphable**, so graphing up to 1056 should remove *its* dispatch
overhead and shrink the sawtooth. Confirmed.

`vllm serve` (default block=1056, ladder→1056, util 0.85; KV 922,185 tok; capture 5 s / 0.48 GiB):
```bash
vllm serve Qwen/Qwen3.6-35B-A3B-FP8 --served-model-name Qwen/Qwen3.6-35B-A3B \
  --max-model-len 8192 --gpu-memory-utilization 0.85 \
  --enable-prefix-caching --enable-chunked-prefill --language-model-only \

```

| L | eager block=1056 | **graphs→1056** | Δ |
|--:|--:|--:|--:|

| 3168 (3×1056) | 79.7 | 79.9 | — |

Sawtooth amplitude **1.57× → 1.16×**: non-aligned lengths dropped ~35 ms (the graphed 832-remainder's
dispatch); aligned (3168, 4224) unchanged (single >1056 chunk, eager either way, but already 1-pass).

### Mechanistic model (this is the payoff — we now predict, not just measure)
`TTFT ≈ Σ_chunks ( GPU_compute(chunk_tokens) + dispatch_overhead·[chunk not graphed] )`, where chunks
come from the block-aligned prefill split and a CUDA graph zeroes the dispatch term for any chunk ≤ the
max captured rung. Knob signs: block↑ → fewer passes but bigger graph-workspace + coarser cache;
captures↑ → remove dispatch for more chunk sizes; prefix cache → block-granular reuse.

**Next prediction (untested):** graph the *big* chunk too (captures up to ~3168/4224) → both passes
graph → slow band collapses to the aligned ~90–95 ms band, sawtooth ~gone, **at block=1056 with caching
intact** (no block=8192). Capture workspace at block=1056 is small (1056-rung = 0.48 GiB), so a ~3168
rung ≈ a couple GiB — likely fits at lower util on H100, trivially on H200.

### Reality check — real prompts (not random ids)
All prior numbers used random token-ids + 5 out-tok (never inspected output). Spot-checked with real
chat prompts on this server (`/tmp/real_test.py`): short "capital of France?"→`Paris` (30 ms); medium
(189 tok)→correct "oxygen" w/ quote (35 ms); long (2108 tok)→correct "fruits+seeds" (60 ms). **Cache
path:** same 2105-tok context with two *different* questions → context reused (50% hit) and two distinct
correct answers ("chlorophyll → absorb light"; "Roman roads → development of Europe"). Outputs coherent,
latencies track the random-id measurements. Numbers are real. (Full benchmark TODO.)

### Not viable / ruled out
- `--no-enable-chunked-prefill` (to force 1-pass) → **rejected by vLLM**: prefix caching needs mamba
  cache mode 'align', which requires chunked prefill. So caching and chunked-prefill are coupled.
- Padding prompts to 1056-multiples → works mechanically (aligned = 1-pass) but not production-viable
  (filler pollutes context, cache boundary drifts per turn).
- Cold 4k @ ~90 ms **and** warm caching can't both hold in vLLM 0.22 for arbitrary lengths (chunk =
  attn block = cache granularity, one knob). Warm <50 ms is reachable (tail reprefill is 1-pass +
  graphable); cold-90 needs block=8192 (no cache). True decouple needs SGLang-style separate pools.

## G7 — big-chunk graph (the cold-4k → ~90 ms prediction): blocked on H100 memory
Prediction (from the G5 model): graph the *big* chunk of the 2-pass too → both passes graph → the
cold 3k–5k slow band collapses to the aligned ~90–95 ms band, sawtooth ~gone, at block=1056 with
caching. The big chunks for 3k–5k cold prefill are exactly the block-multiples below the prompt:
3000→2112, 3500/4000/4096→3168, 4500/4752/5000→4224 (remainders ≤1056, already graphed). So the rungs
needed are just {2112, 3168, 4224}.

**Result: OOM on H100 80GB — untestable here (not falsified).**
- Each large PIECEWISE prefill capture is **~6–8.5 GiB** (4224→8.51, 3168→6.38). Ladder {…,2112,3168,4224}
  needs ~30+ GiB of capture pool; model 33.6 GiB + pool > 80 GiB.
- Lowering `--gpu-memory-utilization` 0.60→0.45 did **not** help — in-use stayed ~78.45 GiB (KV was
  already minimal; the captures dominate). Dropping 4224 still OOM'd on 3168.
- **H100 graph ceiling ≈ 2112 tokens/chunk** (2112 captured fine; 3168 OOM'd). So warm-tail (≤1056) and
  small/mid prompts (≤~2k) graph; the 3k–5k cold big chunk does not.

**Needs H200 (141 GB)** — the case anticipated all along. There the {2112,3168,4224} rungs (and
5280/6336/7392 for the full 0–8k cold path) fit, the prediction is a 5-min relaunch to test, and HBM3e
~4.8 TB/s (~1.4× H100) also drops the weight-read floor on warm + cold.

## G8 — with the dispatch floor gone, attack the MoE? DeepGEMM backend = not worth it
With CUDA graphs killing the launch/idle floor, the biggest remaining GPU cost is the **MoE expert GEMM**
(`fused_moe_kernel`, ~23 ms / ~37% @4000, E-repro-7). Forced the DeepGEMM MoE kernel: `--moe-backend
deep_gemm` (log: "Using DEEPGEMM Fp8 MoE backend"; +2785-kernel DeepGEMM warmup). Profiled L=4224 (1-pass):

| | Triton (auto) | DeepGEMM (forced) |
|---|---:|---:|
| MoE matmul (×80: w13 `1024×2048` 13.13 + w2 `2048×512` 7.85) | 22.99 ms | **20.97 ms (−9%)** |
| total GPU busy (1-pass L=4224) | ~63 ms | 65.4 ms (1804 vs 1724 kernels) |
| **cold TTFT @4000** (2-pass) | **109 ms** | **128 ms** |
| cold TTFT @4224 (1-pass) | 93.8 ms | 95.7 ms |

DeepGEMM's matmul **is** ~9% faster (confirms E12's "~8% faster matmul"), but its grouping/transpose/permute
kernels (+80 kernels) more than eat the win → **net TTFT worse** (and the 2-pass non-aligned lengths amplify
it: 4000 +19 ms). **Auto-Triton is correct; reverted.**

**Why kernel choice can't help:** the MoE is **bandwidth-bound** — it reads the full **32 GB FP8 expert
weights** every prefill (E-repro-7: ~9.6 ms HBM floor; matmul *compute* ~0.1 ms). A faster GEMM barely
moves a weight-read-bound kernel, and DeepGEMM even adds traffic. The ~21–23 ms MoE floor **is** the weight
read.

### Conclusion: at the compute/bandwidth floor on H100
With graphs removing dispatch and the MoE pinned to the 32 GB weight read, H100 is at its floor. The only
remaining levers are **not** software:
- **W4/INT4 experts** → ~half the weight read → lower MoE floor
- **H200** (HBM3e ~4.8 TB/s ≈ 1.4×) / **B200** → the 9.6 ms read floor drops proportionally (also unblocks
  the G7 big-chunk graphs)

Kernel/backend tuning (Triton config E11, DeepGEMM E12/G8) is exhausted — all confirm the same BW floor.

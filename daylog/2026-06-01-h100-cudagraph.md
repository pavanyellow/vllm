# 2026-06-01 (H100) — CUDA-graph capture is the TTFT dispatch floor

Pursuing the lever the repro log kept pointing at: prefill is **host-dispatch bound**
(`2026-06-01-h100-repro.md` E-repro-6: L=300 = 81 ms wall / 15.7 ms GPU-busy = 19% util,
~60 ms eager-launch idle; the unexplained L=16→20 floor step in E-repro-4). A collaborator's
A100/INT8 report (`serve-qwen36-a100` branch) found vLLM only graph-captures **decode** sizes,
so prefill runs PIECEWISE/eager — and extending captures gave −40–65% TTFT. Checked it against
our FP8/H100 setup; it transfers. Same box/model as the repro log.

## Root cause: the capture cliff = our `--max-num-seqs 8`
The recommended config's `--max-num-seqs 8` caps `max_cudagraph_capture_size` at **16**:
```
cudagraph_capture_sizes: [1, 2, 4, 8, 16]      # mixed prefill-decode, PIECEWISE
```
So prefill ≤16 tokens runs a captured graph; **>16 falls to no-graph (eager)**. Runtime maps a
request of N tokens to the smallest captured rung ≥ N (`cudagraph_dispatcher.py:76-95`, round-up);
N > max → `CUDAGraphMode.NONE`. This is exactly the E-repro-4 floor step at L=16→20.

GPU-busy flat ~10 ms throughout; wall jumps 22→70 ms at the 16→20 cliff. The graph removes

puzzle (why L=15 stayed fed but L≥20 starved): L≤16 runs a graph; L>16 dispatches ~1720 kernels eagerly.

## G2 — extend captures to 104 → the overhead collapses (−70%)
Relaunched with `--compilation-config '{"cudagraph_capture_sizes":[1,2,4,8,16,24,32,40,48,56,64,72,80,88,96,104]}'`.
Capture cost: **16 rungs in 4 s, +0.28 GiB** (vs 0.13 GiB for 5 rungs — small rungs are ~free).

| L | baseline (≤16) | **extended (≤104)** | Δ |
|--:|--:|--:|--:|
| 12 | 22.2 | 22.4 | — |
| 20 | 69.9 | 22.3 | **−68%** |
| 32 | 74.3 | 22.3 | **−70%** |
| 50 | 75.7 | 22.5 | **−70%** |
| 64 | 74.4 | 22.8 | **−69%** |
| 80 | 76.3 | 22.7 | **−70%** |

Step gone — **flat ~22 ms from 12 to 100**, at the graphed floor (~10 ms GPU + ~12 ms graph-replay +
eager attention/mamba split-ops, which stay outside the PIECEWISE graph). Beats the A100/INT8 report's
−62% @L=50 (we're on faster H100 + the cliff was lower for us).

## How to set it / cost
- CLI: `--compilation-config '{"cudagraph_capture_sizes":[...]}'` (max rung → `max_cudagraph_capture_size`).
- Memory is set by the **largest** rung (one persistent workspace), not the count; rung count only
  costs capture time (~0.13 s/rung small) + padding granularity (round-up to next rung).

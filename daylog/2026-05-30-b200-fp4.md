# 2026-05-30 Day Log — Qwen3.6-35B-A3B-**NVFP4** on **B200**

First day on Blackwell. Goal: move the TTFT-characterization work off H100/FP8 onto
**B200 + NVFP4** (`nvidia/Qwen3.6-35B-A3B-NVFP4`), the NVIDIA Model-Optimizer build
released 2026-05-28. NVFP4 is a native Blackwell datatype, accuracy is within noise of
BF16 (MMLU-Pro 85.0 vs 85.6, GPQA 84.8 vs 84.9, AIME 88.8 vs 89.2 per the model card),
and the checkpoint is ~3x smaller (19B on disk), so it should free up the KV headroom that
forced `--max-num-seqs 8` on the 80 GB H100.

## Environment
- **GPU:** NVIDIA B200, 183 GiB, compute cap 10.0 (sm_100), driver 580.105.08
- **torch** 2.11.0+cu130, **transformers** 5.9.0, **flashinfer** 0.6.11.post2
- **HF_HOME** = `/workspace/.hf` (weights land here, *not* `~/.cache/huggingface`)
- vLLM was a **custom local build** `vllm-0.22.0-cp38-abi3` (cu130), installed to site-packages.

## Blocker — 0.22.0 release can't load the NVFP4 checkpoint
Launched the card's canonical command on the installed **0.22.0**:
```
vllm serve nvidia/Qwen3.6-35B-A3B-NVFP4 --port 8000 --quantization modelopt \
  --reasoning-parser qwen3 --max-model-len 65536 --gpu-memory-utilization 0.9
```
Weights downloaded fine (57 s), then engine init **crashed**:
```
ValueError: There is no module or parameter named 'lm_head.input_scale' in
Qwen3_5MoeForCausalLM. Available params for lm_head (ParallelLMHead): {'lm_head.weight'}
```
**Root cause:** this checkpoint quantizes **`lm_head` itself to NVFP4** — confirmed by
inspecting the safetensors: `lm_head.weight` is `U8 [248320,1024]` (two FP4/byte) +
`weight_scale F8_E4M3 [248320,128]` (per-16 block) + global `weight_scale_2`. The 0.22.0
release builds an *unquantized* `ParallelLMHead` for the new `Qwen3_5Moe` arch (only
`lm_head.weight`), so the extra scale tensors have nowhere to land. The HF card explicitly
says to start from `vllm/vllm-openai:nightly` — support for the quantized `lm_head` on this
2-day-old arch only exists in nightly, not the 0.22.0 release.

`quant_method=modelopt v0.37.0`, `quant_algo` mixed FP8 + NVFP4 (`modelopt_mixed`);
`ignore: ['mtp*']`. lm_head sits in the 4-bit `group_1`.

## Fix — in-place upgrade to nightly (no Docker available here)
No docker client (already inside a container, can't nest). Public nightly is only
**`0.22.1rc1.dev22+g3fd9d2d35`** — 22 commits past 0.22.0, same `cp38-abi3` tag, so deps
match and ABI risk is low. Steps:
1. Backed up the working install: `logs/vllm-0.22.0-install-backup.tgz` (261 MB,
   tar of site-packages `vllm/` + `vllm-0.22.0.dist-info/`). **This is the only rollback** —
   the original cu130 wheel is gone from `dist/` and not in pip cache.
2. Stashed nightly wheel in `dist/`.
3. `pip install --no-deps --force-reinstall` the nightly wheel (so torch/flashinfer untouched).
4. `import vllm` → clean. No ABI breakage.

Relaunched same command on nightly → **boots**. Model load 20.37 GiB / 27 s, cold start
**343.7 s** (~5.7 min, comparable to H100). Coherence sanity passed (`"...Paris."`).

## Serving facts (NVFP4 / B200)
- Model weights: **20.37 GiB** (vs ~40 GiB FP8/BF16).
- **Available KV cache: 132.9 GiB → 6,551,614 tokens → ~100x max concurrency** at 65k ctx.
  This is the big win vs H100: the FP8/H100 run was KV-starved and capped at `max-num-seqs 8`;
  here KV is effectively unconstrained for the 3k–5k workload.
- Attention backend: **FLASHINFER**. MoE backend: **MARLIN** (auto-selected) — *suboptimal*;
  Blackwell FP4 paths `FLASHINFER_TRTLLM / FLASHINFER_CUTLASS / FLASHINFER_CUTEDSL` were all
  available but not chosen. **Top lever for next session.**

`ttft_sweep.py --lengths 3000,3168,3500,4000,4096,4224,4500,4752,5000 --concurrency 1 --n 12 --warm 4`
(`--model nvidia/Qwen3.6-35B-A3B-NVFP4`; cache_frac=0.0). Lengths chosen to straddle the
1056-chunk boundaries (3168=3x, 4224=4x, 4752=4.5x). Raw → `logs/ttft-baseline-nvfp4-b200.txt`.

```

   3000     187.1     195.9     182.3
   3168     183.7     189.1     179.3   <- 3x1056
   3500     181.9     191.5     178.7
   4000     195.0     201.5     182.8
   4096     192.8     221.2     177.2
   4224     198.5     220.9     178.1   <- 4x1056

```

**Findings:**
1. **The H100 sawtooth is gone.** On H100/FP8 stock swung 95→180 ms with sharp spikes at the
   1056-aligned lengths; here it's **flat ~182–200 ms, gently rising**, and the aligned lengths
   (3168/4224/4752) do *not* spike (4224 sits with its neighbors). So the chunk-alignment
   penalty that motivated `--block-size 8192` does not reproduce on the nightly engine — the
   `--block-size 8192` trick may be unnecessary here. (Needs confirmation: re-run with block-size
   8192 to A/B.)
2. **Absolute TTFT is higher than H100/FP8's best (88–103 ms).** Strongly suspect the **MARLIN
   MoE backend** — it's a generic kernel, not the Blackwell FP4 tensor-core path. This, not the
   block size, is the thing to fix.

## E2 — Kernel profiler attribution (`--block-size 8192`, C=1)
Profiling API changed in nightly: the `VLLM_TORCH_PROFILER_DIR` env var is gone, replaced by
`--profiler-config '{"profiler":"torch","torch_profiler_dir":...,"torch_profiler_record_shapes":true,
"torch_profiler_with_flops":true}'` + the `/start_profile` and `/stop_profile` POST endpoints.
Driver `profile_prefill.py`: per length, warm 4 prefills → `/start_profile` → 1 prefill
(random tokens, `max_tokens=1`) → `/stop_profile`. Parser `parse_trace.py` aggregates **leaf GPU
kernels only** — must EXCLUDE the `user_annotation`/`gpu_user_annotation` spans
(`execute_context`, `## Call CompiledFxGraph ##`), which wrap the kernels and double-count
(they alone summed to ~417 ms vs ~85 ms of real kernels).

Side note: `--block-size 8192` on this hybrid model also needs **`--max-num-seqs ≤ 850`** — init
fails otherwise (`max_num_seqs (1024) exceeds available Mamba cache blocks (850)`: each decode seq
needs one Mamba state block). Used `--max-num-seqs 512`. KV with bs=8192: 5.1M tokens / 78x (vs
6.55M at stock bs) — same "KV-for-TTFT" trade noted on H100, but still huge headroom.

**Leaf GPU-kernel time per prefill: L=4096 → 79.7 ms, L=4224 → 85.0 ms** (identical mix → no
sawtooth, cost is structural). Component rollup @ L=4224:

| component                | ms   |   %  | note |
|--------------------------|-----:|-----:|------|
| **MoE — Marlin FP4**     | 49.6 | 58%  | expert matmuls |
| MoE — CUTLASS gemm       |  9.5 | 11%  | shared-expert / gating |
| Linear-attn / GDN        |  7.9 |  9%  | gated-delta-net (Mamba path) |
| glue (elemwise/quant/norm/reduce) | ~7 | 8% | |
| **Attention (FlashInfer)** | 1.3 | 1.5% | real softmax attn (few layers) |

**Actual kernel names** (the smoking gun is the top row, 52–55% of all GPU time):
```
void marlin_moe_wna16::Marlin<...>            45.0 ms / 80 calls   <- experts
void marlin::Marlin<...>                       4.5 ms / 80 calls
_ZN7cutlass...GemmUniversal... (sm100)         5.7 ms              shared-expert gemm
chunk_gated_delta_rule_fwd_kernel_h_blockdim64 4.4 ms ┐
chunk_fwd_kernel_o / chunk_scaled_dot_kkt_fwd  3.1 ms ├ gated-delta-net
_causal_conv1d_fwd_kernel / recompute_w_u_fwd  2.9 ms ┘
merge_16x16_to_64x64_inverse_kernel            3.4 ms              GDN state merge
vllm::moe::topkGating<8,256,4,...>             2.3 ms              expert routing
fmhaSm100fKernel_...PagedKvCausal...H256...    1.3 ms              FlashInfer attn (sm100)
nvjet_sm100_qqtst_... (cublas sm100)          ~0.5 ms              dense gemms
```

**Finding 1 — MoE is on the wrong kernel.** `marlin_moe_wna16` = **W4A16**: 4-bit weights
*upconverted to bf16*, matmul done in bf16 on the generic Marlin kernel. It does **not** use
Blackwell FP4 tensor cores. vLLM auto-picks MARLIN because `VLLM_USE_FLASHINFER_MOE_FP4` defaults
OFF (the card's DGX-Spark example even sets it `=0`; on B200 sm_100 we want `=1`). This single
change targets ~58% of GPU prefill time and is the likely cause of NVFP4/B200 being ~2x the
H100/FP8 TTFT.

**Finding 2 — launch/overhead-bound.** GPU busy only ~85 ms but the forward span
(`execute_context`) is ~253 ms and wall ~280 ms → large inter-kernel idle. Matches the H100
"memory-bound MoE + ~20 ms fusable overhead" note. Fixing the MoE kernel should also cut launches.

Artifacts: `profile_prefill.py`, `parse_trace.py`, traces in `profiles/`,
serve log `logs/serve-profile-bs8192.log`.

## E3 — "Fix" the MoE backend: try a pure-NVFP4 checkpoint (negative result)
Hypothesis from E2: Marlin runs the experts as **W4A16** (4-bit weights upconverted to bf16,
matmul on bf16 tensor cores) and never touches Blackwell FP4 tensor cores. NVIDIA's own recipe
also pins `--moe-backend marlin` + `VLLM_USE_FLASHINFER_MOE_FP4=0`, and forcing FlashInfer FP4 on
the nvidia checkpoint threw `NotImplementedError`. Root cause traced to the nvidia checkpoint's
expert **input_activations being static** (`dynamic: False`) — the FlashInfer FP4 MoE kernels want
**dynamic** activation quant.

Found pure-NVFP4 (no-FP8) checkpoints that use dynamic ("local") FP4 activations:
`RedHatAI/Qwen3.6-35B-A3B-NVFP4` and `unsloth/...NVFP4` (compressed-tensors; experts NVFP4 W4A4,
attention/gates/lm_head left in bf16, lm_head NOT quantized → also sidesteps the original boot crash).

Launched `RedHatAI/...NVFP4` with `VLLM_USE_FLASHINFER_MOE_FP4=1` → it **engaged
`FLASHINFER_TRTLLM`** (native FP4 tensor-core MoE) instead of Marlin. So the kernel swap worked.

**But TTFT got WORSE.** Same sweep, C=1, stock config (raw: `logs/ttft-redhat-fp4-trtllm.txt`):

| in_len | nvidia Marlin (W4A16) p50 | RedHatAI FP4-TRTLLM p50 | Δ |
|-------:|--------------------------:|------------------------:|----:|
| 3000   | 187 | 204 | +17 |
| 3500   | 182 | 209 | +27 |
| 4000   | 195 | 232 | +37 |
| 4096   | 193 | 236 | +43 |
| 4224   | 198 | 227 | +29 |
| 5000   | 216 | 236 | +20 |

FP4-TRTLLM is **consistently ~20–40 ms slower** for TTFT at C=1. Why:
1. **TTFT @ C=1 is not MoE-compute-bound.** ~4k-token prefill, single stream → ~130 tokens/expert
   (small-M GEMM) → launch/bandwidth-bound. FP4 tensor cores only win when compute-bound (big
   batch). The TRT-LLM FP4 kernel, tuned for throughput, has more per-call overhead at small M
   than Marlin. So FP4 MoE is a **throughput lever, not a TTFT lever.**
2. RedHatAI keeps **attention in bf16**; nvidia keeps it in **FP8** (native FP8 tensor cores), so
   RedHatAI also loses the faster attention path.

## Conclusion (TTFT @ C=1, single-stream 3k–5k)
- **H100 / FP8 + `--block-size 8192`: ~88–103 ms — still the winner.**
- B200 / nvidia-NVFP4 / Marlin-W4A16: ~182–216 ms.
- B200 / RedHatAI-NVFP4 / FP4-TRTLLM: ~204–236 ms (worst).

NVFP4 on B200 did **not** help TTFT, for this workload. NVFP4 is a capacity + bandwidth + (high-
concurrency) throughput play — its compute advantage needs batch we don't have at C=1. For pure
single-stream TTFT, stay on H100/FP8. The B200/NVFP4 story would only get interesting at higher
concurrency (throughput) — not pursued (out of scope: TTFT-only).

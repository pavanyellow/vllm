# 2026-06-02 (H200) — `--max-num-seqs` 8 vs 32: closing the 500-call cliff

Follow-up to [`2026-06-02-h200-voice-concurrency.md`], whose Open list asked to
"sweep call count 250/300/400 to pin … the peak→32 saturation point." Here we push
past the knee to **500 calls** and isolate the one knob that governs the cliff:
`--max-num-seqs` (the batch-slot ceiling). Same H200 141GB, vLLM 0.21.0, single GPU,
`Qwen/Qwen3.6-35B-A3B-FP8`.

## Serving config

Identical to the prior daylog except we sweep `--max-num-seqs` between **8** and **32**
(and run the stock block list — no `--fingerprint-mode`, port 8080):

```bash
vllm serve Qwen/Qwen3.6-35B-A3B-FP8 --served-model-name Qwen/Qwen3.6-35B-A3B \
  --host 127.0.0.1 --port 8080 \
  --max-model-len 8192 --gpu-memory-utilization 0.85 \
  --enable-prefix-caching --enable-chunked-prefill --language-model-only \
  --reasoning-parser qwen3 --default-chat-template-kwargs '{"enable_thinking":false}' \
  --max-num-batched-tokens 8192 --max-num-seqs {8|32} \
  --compilation-config '{"cudagraph_capture_sizes":[1,2,4,8,16,24,32,40,48,56,64,72,80,88,96,104,128,256,384,512,640,768,896,1024,1056,2112,3168,4224]}'
```

Driver (same voice model, mix 30/30/40, 4k ctx, cache ON, 75 s, max_tokens=80):

```bash
for N in 100 200 500; do
  python voice_sim.py --calls $N --duration 75 --ctx-min 3000 --ctx-max 5000 --groups 30,30
done
```

## The sweep

**`--max-num-seqs 8`:**

| | 100 | 200 | 500 |
|---|---:|---:|---:|
| throughput (req/s) | 6.7 | 13.0 | 18.6 |
| TTFT p50 (ms) | 50.2 | 75.9 | 8,348.3 |
| TTFT p90 (ms) | 78.0 | 601.1 | 13,265.5 |
| TTFT p99 (ms) | 101.8 | 1,245.1 | 14,969.8 |
| peak in-flight | 9 | 37 | 302 |
| avg in-flight | 1.30 | 4.90 | 168.67 |

**`--max-num-seqs 32`:**

| | 100 | 200 | 500 |
|---|---:|---:|---:|
| throughput (req/s) | 6.6 | 13.3 | 28.9 |
| TTFT p50 (ms) | 51.8 | 73.6 | 207.2 |
| TTFT p90 (ms) | 92.8 | 110.1 | 4,581.8 |
| TTFT p99 (ms) | 205.4 | 290.1 | 6,773.0 |
| peak in-flight | 10 | 26 | 229 |
| avg in-flight | 1.37 | 3.77 | 53.30 |

## Read

- **100 & 200 calls are indifferent to the knob.** Real in-flight concurrency never
  exceeds ~26, so an 8-slot vs 32-slot ceiling barely registers — p50 stays ~50–75 ms
  in both. This confirms V4: below the knee the system is latency-bound, the batch
  is mostly idle, and slot count is not what's binding.
- **500 calls is where the ceiling bites.** With **8 slots** the engine can't drain
  the arrival rate: avg in-flight piles to **169** (peak 302), the queue blows up, and
  TTFT collapses to **p50 8.3 s / p99 15 s** — a hard cliff, not a graceful slope.
  Raising to **32 slots** removes it: avg in-flight drops to **53**, throughput rises
  **18.6 → 28.9 req/s (+55 %)**, and TTFT recovers to **p50 207 ms / p99 6.8 s** —
  a ~40× p50 improvement at the same load.
- So the prior "knee at ~200 calls" was partly an artifact of the **8-slot** default.
  At 32 slots, 500 calls is degraded-but-serving (p99 ~6.8 s — not interactive, but
  not collapsed). The interactive-SLO knee (p99 ≤ ~250 ms) is still ~200 calls; the
  *saturation* point moved well past 500.

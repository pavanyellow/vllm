# 2026-06-01 (H100) — KV / prefix-cache path: re-serving a 4k prompt with the tail changed

Scenario: a 4000-token prompt was already served (KV in the prefix cache); a new
request shares the first (4000−N) tokens and changes the **last N** (N=10…500…).
What's the TTFT and what gets recomputed? Same box/model as `2026-06-01-h100-repro.md`
(H100 80GB, vLLM 0.22.0). Builds on that file's finding that prefill is
host-dispatch / weight-read floor-bound (E-repro-6/7).

Method: `kv_suffix.py` — prime a fixed 4000-tok prompt, then send `orig[:4000−N] +
fresh(N)`, raw token-ids → /v1/completions, TTFT = first streamed chunk, p50 of 8
samples; prefix-cache hit% from /metrics deltas. `kv_prof.py` profiles one reuse
request (torch profiler).

## K1 — block=8192 (the recommended config): NO reuse at all
`kv_suffix.py --len 4000 --changed 0,10,20,50,100,500` on the E9 default config
(`--block-size 8192 --max-num-seqs 8`):

| changed N | shared | TTFT p50 | hit% | vs cold |
|--:|--:|--:|--:|--:|
| 0 (identical) | 4000 | 88.9 | 0 | −0.6 |
| 10 | 3990 | 87.6 | 0 | 0.8 |
| 50 | 3950 | 81.7 | 0 | 6.7 |
| 100 | 3900 | 88.6 | 0 | −0.2 |
| 500 | 3500 | 87.9 | 0 | 0.5 |

full-cold (fresh 4000, 0 reuse) = 88.4 ms. **hit% = 0 for every N, including N=0.**
A 4000-token prompt is < one 8192-token block, so it produces **zero complete cache
blocks** → even re-serving the *identical* prompt reprefills all 4000 (~88 ms). The
block=8192 choice that kills the TTFT sawtooth (repo E9) also **fully defeats prefix
caching for any prompt < 8192 tokens**. (N=20/50 dips are noise, not hits.)

## K2 — stock block=1056 (caching works): block-granular, with a cliff
Relaunched stock (no `--block-size` → 1056; `--max-model-len 32768`; prefix caching
on). 4000 tok = 3 full blocks (3168) + 832 partial. `kv_suffix.py --changed
0,10,50,100,500,800,900,1100,1900,2100,3000,3500`. full-cold(4000)=153.8 ms (the 1056
**sawtooth** slow band — 4000 splits into 2 passes; cf. repo E8).

| changed N | shared | TTFT p50 | hit% | saved |
|--:|--:|--:|--:|--:|
| 0 | 4000 | 91.3 | 79 | 62.5 |
| 10 | 3990 | 87.5 | 79 | 66.4 |
| 50 | 3950 | 85.0 | 79 | 68.8 |
| 100 | 3900 | 87.0 | 79 | 66.8 |
| 500 | 3500 | 91.8 | 79 | 62.1 |
| 800 | 3200 | 88.7 | 79 | 65.1 |
| **900** | 3100 | **156.9** | **0** | −3.1 |
| 1100–3500 | … | 148–158 | 0 | ~0 |

- **Block-granular reuse:** last-10 and last-800 changed cost the *same* ~88 ms — reuse
  rounds down to the 1056 boundary (3 blocks = 3168 tok reused; hit% = 3168/4000 = 79%).
- **Cliff at N=832** (the 3rd-block boundary): once the change reaches before token 3168,
  reuse collapses to 0% and TTFT snaps back to the full 154 ms sawtooth. (Observed: it
  drops straight to 0%, not the 2-block/1-block intermediate steps block-arithmetic would
  predict — vLLM appears to stop reusing past the first diverging block here; not chased.)

## K3 — profiling a reuse prefill vs full cold, and the punchline
`kv_prof.py --changed 50` (3168 cached, ~832 reprefilled) vs `prof_prefill.py --len 4000`
(full cold), both block=1056, torch profiler:

| | reuse (last-50) | full cold 4000 |
|---|--:|--:|
| device kernels | 1728 (1 pass) | **3452 (2-pass sawtooth)** |
| Σ GPU busy | **25.1 ms** | 78.7 ms |
| moe_grouped_gemm | 11.0 (×80) | 30.9 (×160) |
| dense_gemm | 4.1 | 13.7 |
| elementwise/norm | 4.0 | 11.6 |
| lin_attn_gdn | 2.1 | 9.5 |
| TTFT (wall, K2/E8) | ~85 ms | ~154 ms |

Caching cuts **GPU compute 3.1×** (78.7→25.1 ms) but **TTFT only ~1.8×** (154→85 ms).
The gap is the **~1720-kernel eager-dispatch floor (~60 ms GPU-idle)** from the repro log
(E-repro-6) — paid for *any* non-empty reprefill regardless of how few tokens are new.
The MoE GEMM stays large even for 832 new tokens (11 ms) because all 256 experts still
hit → full 32 GB weight read (the per-forward floor again).

### Cross-config takeaway
For re-serving a 4k prompt with the tail changed:
- **block=8192 (no caching):** ~88 ms flat, any change (one fast single-chunk pass).
- **block=1056 (+caching):** ~88 ms when the change is in the last 832 tok (reuse hits),
  else ~154 ms (sawtooth, reuse lost).

So block=8192's *no-cache* 88 ms **ties** block=1056's *cached* 88 ms and beats it when
reuse is lost. **Prefix caching does not help this path** — the floor (32 GB weight read
+ ~1720-kernel dispatch) is paid per forward, and block=8192 already does the whole 4k in
one fast pass. The real lever for re-serve latency is the dispatch floor (CUDA-graph the
prefill / cut kernel count), not the KV cache.

# 2026-05-30 (2×H100)

Continues `2026-05-30-h100.md` (E8–E12, single H100 80GB). Shut that box down,
brought up **2×H100 80GB HBM3, NVLink** (links @ ~26.6 GB/s). Question: with a
second card, what does scale-out buy for **single-stream (C=1) prefill TTFT** —
and is it TP, or EP (expert-parallel) for the 256-expert MoE? Metric scope is
C=1 TTFT only (same as E8/E9); throughput-under-load is a separate axis.

## Method
- Same as E8/E9: `ttft_sweep.py --lengths 3000,3168,3500,4000,4096,4224,4500,4752,5000 --concurrency 1 --n 12 --warm 4` (fresh random ids, 0% cache, 5 out-tok, stream; 8 samples/len). `/v1/completions`.
- Same server flags as E9 (the block_size=8192 config that killed the sawtooth): `--max-model-len 8192 --gpu-memory-utilization 0.90 --enable-prefix-caching --enable-chunked-prefill --language-model-only --reasoning-parser qwen3 --default-chat-template-kwargs '{"enable_thinking":false}' --max-num-batched-tokens 8192 --block-size 8192 --max-num-seqs 8`. Only the parallelism flags change between runs.
- Box: 2×H100 80GB, vLLM 0.22.0, torch 2.11.0+cu130, CUDA 13.0, py 3.12. One server at a time on port 8000.

## Setup deltas (mem + KV per config)

| config | parallelism flags | weights/GPU | KV avail/GPU | GPU KV cache |
|---|---|---:|---:|---:|
| gpu=1 | `--tensor-parallel-size 1` (`CUDA_VISIBLE_DEVICES=0`) | 33.65 GiB | 35.94 GiB | **269,165 tok** |
| TP=2 | `--tensor-parallel-size 2` | 16.93 GiB | 52.33 GiB | **782,921 tok** |
| EP | `--tensor-parallel-size 2 --enable-expert-parallel` | 16.93 GiB | 52.19 GiB | **780,580 tok** |

- gpu=1 KV = 269,165 tok — **identical to E9**, so the baseline reproduces exactly on this box.
- TP=2 halves weights/GPU (33.65→16.93) → KV capacity **2.9×** (269k→783k tok). This is the real win of the 2nd card: capacity, not latency.
- EP: same memory picture as TP=2 (experts redistributed, not duplicated). Workers report as `Worker_TP0_EP0` (EP active). EP degree = tp×dp = 2.

## E13 — vLLM TP=2 vs EP vs gpu=1, C=1 TTFT (p50 ms)

| in | gpu=1 | TP=2 | EP | min(gpu1,EP) vs TP2 |
|---:|---:|---:|---:|---|
| 3000 | **84.8** | 107.8 | 88.6 | gpu1 |
| 3168 | **84.7** | 102.5 | 89.3 | gpu1 |
| 3500 | **85.0** | 105.0 | 88.4 | gpu1 |
| 4000 | **91.5** | 108.4 | 89.8 | EP≈gpu1 |
| 4096 | **92.1** | 101.8 | 95.7 | gpu1 |
| 4224 | **91.3** | 102.3 | 88.7 | EP |
| 4500 | **98.4** | 104.1 | 94.9 | EP |
| 4752 | 101.3 | 99.6 | **98.1** | EP |
| 5000 | 107.4 | **99.7** | 101.8 | TP2 |

Three distinct **shapes**, and the shape is the finding:
- **gpu=1 rises with length** (84.8 → 107.4): classic prefill compute scaling, no comms. Best below ~4500.
- **TP=2 is ~flat ~100–108**, length-insensitive: a fixed allreduce floor (2 allreduces × 40 layers on the C=1 critical path) dominates and masks the compute term. Worst at short prompts, only wins at the long end (5000) where halved per-GPU compute finally beats the fixed comms cost.
- **EP tracks gpu=1** then flattens: swaps TP's per-layer allreduce for routed all-to-all (only top-8/256 experts move) **and** keeps experts whole (efficient grouped GEMM vs TP's sliced-thin experts). ~10–15 ms faster than TP=2 across the board; edges out gpu=1 at ≥4752.

**Crossover ≈ 4700 tok.** Below it, single GPU wins (no comms to amortize). Above it, scale-out (EP ≳ TP) wins. Ordering: **EP ≤ gpu=1 ≤ TP=2** at short; **EP ≈ TP=2 < gpu=1** at long.

## Why no 2× from TP (weights are split — shouldn't matmuls halve?)
They do halve per-GPU, but E10 already measured prefill at **66 ms GPU-busy vs 15 ms roofline (4.4× gap)** — C=1 prefill is overhead-bound (kernel launches, FP8 quant, linear-attn/mamba ops, small grouped-MoE GEMMs), not FLOP/weight-bandwidth-bound. TP halves the part that **wasn't** the bottleneck and **adds** allreduce. Amdahl → ~wash, slightly worse. Only ~3B of 35B params are active, so the split compute is small vs fixed cost; and slicing experts thinner drops GEMM efficiency. Net: the 2nd GPU buys **KV capacity / concurrency**, invisible at C=1. EP recovers the small loss because all-to-all moves less data than dense allreduce and experts stay whole.

## E14 — SGLang, same triple (gpu=1 / TP=2 / EP), C=1 TTFT (p50 ms)
Cross-check the result on a different engine. SGLang 0.5.12.post1 (cu130 venv), same model, same `ttft_sweep.py` over `/v1/completions:30000`. Flags per E-SG1: `--context-length 32768 --mem-fraction-static 0.90 --chunked-prefill-size 8192 --reasoning-parser qwen3`. Parallelism: gpu=1 `--tp-size 1`; TP=2 `--tp-size 2`; EP `--tp-size 2 --ep-size 2`. KV (separate mamba/KV allocators, page_size=1): gpu=1 **1,006,799 tok** (= E-SG1), TP=2 / EP **2,909,136 tok** (2.9×).

| in | gpu=1 | TP=2 | EP |
|---:|---:|---:|---:|
| 3000 | **80.6** | 96.6 | 98.9 |
| 3168 | **88.4** | 97.3 | 98.3 |
| 3500 | **84.2** | 96.0 | 99.2 |
| 4000 | **89.7** | 96.0 | 98.3 |
| 4096 | **90.6** | 96.7 | 99.9 |
| 4224 | **90.1** | 101.7 | 96.6 |
| 4500 | **96.5** | 98.8 | 99.8 |
| 4752 | **98.8** | 97.6 | 104.6 |
| 5000 | 101.5 | **98.0** | 101.6 |

Same two shapes as vLLM: **gpu=1 ramps with length** (80.6→101.5), **scale-out is a flat floor** (~96–99). Crossover ~4700–4800 again (gpu=1 best ≤4500; TP=2 edges it at 5000). gpu=1 SGLang ≈ gpu=1 vLLM.

**One divergence from vLLM: SGLang EP does NOT beat its TP.** EP ≈ TP=2 (~99 vs ~97), if anything marginally worse. At EP=2 the default a2a path's dispatch/combine cost ≈ what it saves vs SGLang's already-efficient grouped-GEMM TP-MoE, so no net win — versus vLLM, where EP recovered ~10 ms over TP. Conclusion holds either way: at C=1, nothing in the expert-routing layout produces a speedup; the win is capacity.

## Takeaway (both engines)
- **C=1 latency: a 2nd GPU does not make a single request faster.** Both vLLM and SGLang show gpu=1 winning below ~4700 tok and scale-out only a flat ~97–105 ms floor that ties/edges gpu=1 above it. Root cause (E10): prefill is overhead-bound, 4.4× off roofline — TP halves the part that wasn't the bottleneck and adds allreduce.
- **Plain TP is the dominated option.** It gives the same KV capacity as EP but the worst latency. In vLLM prefer **EP** (TP=2 + `--enable-expert-parallel`) — recovers ~10 ms; in SGLang EP ≈ TP, so either is fine.
- **The real win of the 2nd card is capacity:** vLLM 269k→783k tok (2.9×), SGLang 1.006M→2.909M tok (2.9×) — concurrency / long-context headroom, invisible at C=1.
- **If you only serve short single-stream prompts (<4.7k):** run one engine per GPU (DP replicas) rather than one TP=2 engine — two independent gpu=1 servers beat a TP=2 server on both latency and throughput.
- Engine parity: SGLang KV ~3.7× vLLM at equal mem (page_size=1 + separate mamba/KV allocators vs vLLM's unified 8192-block tax); C=1 TTFT within a few ms across all configs.
